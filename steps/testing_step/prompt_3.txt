You are reviewing Julia code that was generated by an AI. The code has just been
EXECUTED for real (JuMP + Gurobi) on a small test instance, and the execution FAILED.
Your job is to fix the cause of the failure.

The code was written by an AI and has not been reviewed by a human. Comments inside it
(including commented-out lines and statements claiming a requirement is satisfied) are
not evidence of anything: judge only what the code actually does.

## What you receive
1. EXECUTION REPORT: how the run ended (status), the Julia error and stack trace, and
   the last lines of standard output. Line numbers in the stack trace refer to the CODE
   below, which is shown with line numbers.
2. CODE
3. TOOL DOCUMENTATION: the real signatures and return types of the helper functions
   the code is allowed to call.

## Scope
- Fix only what makes the execution fail. Do not refactor, rename, reorder or "improve"
  anything that is not part of the cause.
- Do not change the solution policy (how periods are split, what is fixed, in which
  order). If the failure can only be removed by changing policy logic, do not guess:
  report it under "Flagged, not modified".
- Execution stops at the first error, so the report shows only one failure. If the SAME
  root cause appears in several places (for example the same wrong annotation on three
  arguments), fix every occurrence. Do not look for unrelated bugs.
- Anything suspicious that is unrelated to this failure goes under "Flagged, not
  modified". Do not touch it.

## Procedure
Step 1 - Locate. Use the stack trace to find the exact line(s) in the CODE where the
failure originates, and quote them. If the failing line calls a function, check the call
against TOOL DOCUMENTATION: number of arguments, positional vs keyword, argument types.
Step 2 - Diagnose. State the root cause in one or two sentences, in terms of what Julia
actually does (for example, which type the value really has at that point).
Step 3 - Fix. Apply the smallest change that removes the cause.
Step 4 - Verify. Re-read the corrected lines and trace them concretely: the type of each
value, the argument count of each call, and for each argument whether the signature
requires it positional or keyword. Code that parses is not necessarily code that runs.
If your explanation and your code disagree, the code is what counts: redo the fix.
Step 5 - Final pass. Confirm you changed nothing outside the scope above.

## Notes by status
- code_error: the stderr is the primary evidence. Fix the cause it shows.
- timeout: there is no error message. Look for loops that may never terminate and
  solver calls without a time limit, and fix only that.
- no_output / bad_output: the code ran without errors but the solution file is missing
  or invalid. Check that the solution-writing tool is actually called on every path
  that reaches the end of the function.

Return the COMPLETE corrected code (without line numbers) in exactly one ```julia block.
Outside the block, write plain text with:
- Cause: one or two sentences.
- Changes: each change, with the line(s) it touches.
- Flagged, not modified: anything suspicious you left alone, or "None".
